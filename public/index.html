Architecture

One accept loop. Twelve workers. Zero busy-waiting.

A single thread owns the epoll instance and never blocks on I/O. Connections move through a small, explicit state machine — Queued → InFlight → Idle / Draining — so a slow client downloading a large file can never be mistaken for one that's gone idle, and vice versa.

accept → epoll → bounded pool → sequence-gated write-back, with an independent sweep reaping true idle connections only

Correctness

Four real bugs. Found by testing, not by inspection.

Every one of these was reproduced first — the broken behavior captured on camera, so to speak — before anything was changed. Then the fix was verified against the exact same reproduction. Tagged below with the HTTP status code most associated with each failure mode.

500 · CRASH

One bad header, whole process down

A Content-Length header with a non-numeric value threw an uncaught std::invalid_argument from std::stoul on a worker thread — calling std::terminate() and killing every connection on the server, not just the offending one.

Fixed — wrapped in try/catch, validated the parse consumed the full value, and confirmed the process survives the identical probe post-fix.

408 · TIMEOUT

Slow downloads, killed mid-transfer

A large file to a throttled client hit backpressure (EAGAIN) mid-write. The connection was marked Idle anyway — indistinguishable from a genuinely idle one — so the timeout sweep reaped it at the 5-second mark, truncating the download.

Fixed — added a dedicated Draining state with its own timeout. Verified: a 10.5MB file at 200KB/s now completes byte-for-byte, hash-matched.

RACE · ORDER

Pipelined responses, out of order

Two requests pipelined on one connection could be picked up by two different worker threads and written back in whichever order finished first — a real RFC 7230 violation, not a cosmetic issue.

Fixed — a per-connection sequence gate (extract order in, write order out) forces strict FIFO even across separate read events. Reproduced broken, then reproduced fixed, twice.

503 · OVERLOAD

Fd exhaustion, no warning, no mercy

Under an artificially constrained file-descriptor limit and a connection flood, accept() began failing silently — no log line, just a cascade of hung-up connections downstream.

Fixed — a soft ceiling derived from getrlimit() now throttles new accepts before the OS ever refuses one, with the pressure logged directly at the source.

Load testing

Where it bends, and why

Three concurrency tiers, benchmarked with wrk. The goal wasn't a single throughput number — it was finding out which resource gives first: CPU, the work queue, or file descriptors.

Concurrency Req/sec p50 p99 Bottleneck
100 33,172 2.71ms

1,000 20,282 47.59ms

10,000 23,679 136.00ms
queue + graceful 503s

CPU never exceeded ~54% utilization at any tier — the bounded work queue is the actual limiting resource, not the CPU and not (at these levels) file descriptors. At 10,000 connections, 1,578 requests timed out and 40,649 got a clean 503 instead of hanging — the bounded queue degrading exactly as designed under real overload.

Honest scope

What this is, and isn't

Handles correctly

  • Partial reads & pipelined requests
  • Malformed input (400 / 411 / 405)
  • Keep-alive connection reuse
  • Large files under real backpressure
  • Connection floods & fd exhaustion
  • Graceful overload shedding (503)

Doesn't do (yet)

  • HTTPS / TLS
  • Virtual hosting
  • Dynamic routes beyond two
  • Compression (gzip / br)
  • HTTP/2
  • Range requests
